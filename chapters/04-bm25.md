# Лексический поиск: TF-IDF и BM25 {data-kicker="ГЛАВА 4 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Оператор набирает «вернуть уценённый товар». Самая старая идея поиска: найти фрагменты, где встречаются те же слова, и поднять выше те, где совпали редкие и важные слова. Слово «товар» есть в каждом регламенте «Полки» и почти ничего не говорит. Слово «уценённый» встречается в одном документе и говорит почти всё. BM25 превращает эту интуицию в формулу, которую можно посчитать на бумаге.
:::

## От текста к термам

Сначала текст превращают в термы (terms), единицы, по которым идёт сравнение. В лаборатории это три шага: нижний регистр и замена «ё» на «е», выбрасывание стоп-слов («и», «ли», «можно», «сколько»), обрезка окончаний.

```ts
export function terms(text: string): string[] {
  return tokenize(text).filter((t) => !STOP.has(t)).map(stem);
}
// terms('Можно ли вернуть уценённый товар?') → ['верну', 'уцененн', 'товар']
```

Функция `stem` срезает самое длинное окончание из списка, если после него остаётся хотя бы три буквы. «Возврата», «возврате» и «возврат» дают одну основу «возврат», «уценённого» и «уценённые» дают «уцененн». Это грубо, и грубость легко пропустить. В первой версии лаборатории в списке стояли глагольные окончания «ат» и «ят»: «возврат» превращался в «возвр», а «возврата» в «возврат», и формы одного слова переставали совпадать. Окончание «ть» по той же причине срезается только после гласной, иначе «стоимость» и «стоимости» расходятся. Поэтому любой стеммер проверяют на парах форм своих частых слов. Русская морфология богаче любого списка окончаний, и «вернуть» с «возвратом» у такой обрезки остаются разными словами. В продакшене (в рабочей системе) берут стеммер Snowball для русского языка или лемматизатор, который приводит слово к словарной форме. Но даже лемматизатор не свяжет «вернуть» и «возврат»: это разные леммы, и разрыв между словами вопроса и словами документа остаётся главной слабостью лексического поиска.

## TF-IDF

Классическая схема считает вес слова как произведение двух сомножителей. TF (term frequency) показывает, сколько раз слово встретилось во фрагменте. IDF (inverse document frequency) показывает, насколько слово редкое по всей коллекции.

::: formula
::: f
tfidf(t, d) = tf(t, d) · ln(N / df(t))
:::
N означает число фрагментов в коллекции, df(t) показывает, в скольких из них встречается терм t. Балл фрагмента равен сумме по словам запроса.
:::

У TF-IDF два известных недостатка. Вес растёт линейно с числом повторов: фрагмент, где «товар» написан пять раз, кажется в пять раз релевантнее. И длинный фрагмент набирает больше совпадений просто потому, что в нём больше слов.

## BM25

BM25 исправляет оба недостатка двумя параметрами [3]. Параметр k1 задаёт насыщение: первый повтор слова весит много, десятый почти ничего не добавляет. Параметр b задаёт нормализацию по длине: совпадение в коротком фрагменте весит больше, чем в длинном.

::: formula
::: f
score(q,d) = Σ idf(t)·tf·(k1+1) / (tf + k1·(1 − b + b·|d|/avgdl))
:::
Сумма идёт по словам запроса, |d| означает длину фрагмента в термах, avgdl среднюю длину. В лаборатории idf(t) = ln(1 + (N − df + 0,5) / (df + 0,5)), так считает Lucene: вес всегда положительный. Обычные значения k1 = 1,2 и b = 0,75.
:::

## Расчёт руками

Возьмём три коротких документа и запрос «вернуть уценённый товар».

- **A**: «Уценённый товар можно вернуть, только если обнаружен новый недостаток.»
- **B**: «Товар надлежащего качества можно вернуть в течение 14 дней. Товар должен сохранить товарный вид, товар не должен быть в употреблении.»
- **C**: «Бонусы возвращаются на счёт при возврате товара.»

После нормализации у A {{bm25.lenA}} термов, у B {{bm25.lenB}}, у C {{bm25.lenC}}; средняя длина avgdl = {{bm25.avgdl}}. Слово «верну» есть в двух документах (в C стоят «возвращаются» и «возврате», у них другая основа), «уцененн» в одном, «товар» во всех трёх.

| Терм | df | idf | вклад в A | вклад в B | вклад в C |
|---------------|---------------|---------------|---------------|---------------|---------------|
| {{bm25.tv}} | {{bm25.dfV}} | {{bm25.idfV}} | {{bm25.aV}} | {{bm25.bV}} | 0 |
| {{bm25.tm}} | {{bm25.dfM}} | {{bm25.idfM}} | {{bm25.aM}} | 0 | 0 |
| {{bm25.tt}} | {{bm25.dfT}} | {{bm25.idfT}} | {{bm25.aT}} | {{bm25.bT}} | {{bm25.cT}} |
| **итого** | | | **{{bm25.sA}}** | **{{bm25.sB}}** | **{{bm25.sC}}** |

Проверим одну клетку. Для «верну» в A: tf = 1, длина 6 при средней 8,67, поэтому знаменатель равен 1 + 1,2 · (0,25 + 0,75 · 6 / 8,67) ≈ 1,92, числитель 1 · 2,2 = 2,2, а вклад 0,470 · 2,2 / 1,92 ≈ {{bm25.aV}}. Документ A выигрывает за счёт редкого слова «уценённый»: оно одно дало больше, чем все совпадения B вместе.

Теперь посмотрим на параметры. В документе B слово «товар» встречается {{bm25.tfBT}} раза. Вот его вклад при разных k1 (b = 0,75):

| k1 | 0 | 0,5 | 1,2 | 2 | 5 |
|-----------------|---------------|---------------|---------------|---------------|---------------|
| вклад «товар» в B | {{bm25.k1_0}} | {{bm25.k1_05}} | {{bm25.k1_12}} | {{bm25.k1_2}} | {{bm25.k1_5}} |

При k1 = 0 повторы не учитываются вовсе, вклад равен idf. С ростом k1 повторы весят всё больше, а при очень большом k1 формула приближается к линейному TF. Параметр b при k1 = 1,2 даёт {{bm25.b0}} без учёта длины (b = 0), {{bm25.b075}} при b = 0,75 и {{bm25.b1}} при полной нормализации (b = 1): документ B длиннее среднего, и нормализация его штрафует.

Для сравнения TF-IDF на тех же документах даёт A = {{bm25.tfA}}, B = {{bm25.tfB}}, а документ C получает ноль: слово «товар» есть везде, ln(3/3) = 0. BM25 оставляет общему слову маленький положительный вес, и C попадает в выдачу последним, а не исчезает.

## Сильные и слабые стороны

Лексический поиск хорош там, где вопрос и документ говорят одними словами: номера пунктов, артикулы, коды ошибок, названия программ, редкие термины. Он быстрый, не требует модели, легко объясняется («совпали слова такие-то») и почти не ошибается на точных формулировках. На {{corpus.formal}} аккуратных вопросах тестового набора BM25 ставит нужный документ на первое место почти всегда: MRR = {{cmp.bm25.formal.mrr}} (метрика объяснена в главе 10, единица означает идеал). Это число завышено самим набором: q13 «Нужен ли чек для возврата?» дословно совпадает с заголовком раздела FAQ, а q04, q07, q09, q12 и q16 почти повторяют фразы регламентов («Сколько длится гарантийный ремонт?» против «Гарантийный ремонт длится…»).

На {{corpus.colloquial}} разговорных вопросах картина другая: MRR = {{cmp.bm25.colloquial.mrr}}. Первое место BM25 угадал только на части из них: {{ex.collBmTop}}. Здесь хватило одного точного слова: «уценки» в первом вопросе, «вернуть» в вопросе про духи. Промахнулся он на вопросах {{ex.collBmMiss}}: «баллы» вместо «бонусов», «карточка» вместо «карты», «юрлицо» вместо «юридического лица». А на вопросах {{ex.bmEmpty}} BM25 не вернул вообще ничего: ни одно слово вопроса не совпало с термами действующих документов.

::: {.warn data-title="Типичная ошибка"}
Проверить поиск на вопросах, которые инженер сам написал, глядя в регламент. Такие вопросы повторяют слова документа, и на них лексический поиск справляется блестяще, как на наших аккуратных формулировках. Настоящие пользователи пишут иначе. Тестовый набор собирают из журнала реальных обращений, а не придумывают у экрана.
:::

## Практика

1. Начинайте с BM25: это сильная база, с которой сравнивают всё остальное.
2. Нормализуйте одинаково и документы, и запросы, иначе «ё» и «е» разойдутся.
3. Для русского языка подключите стеммер или лемматизатор, проверьте на своих словах, что он склеивает и чего не склеивает.
4. Не трогайте k1 и b без тестового набора; значения по умолчанию разумны.
5. Сохраните отдельную оценку по разговорным вопросам: там лексика слабее всего.

`npm run bm25` печатает расчёт этой главы: df, idf, вклад каждого терма и итоговые баллы.
