# Права доступа и свежесть {data-kicker="ГЛАВА 9 / ДЛЯ ВСЕХ"}

::: lead
Обычный оператор спрашивает: «Сколько бонусов старший смены может начислить в качестве компенсации?». Ответ есть в регламенте, но регламент помечен «только для старших смен». Через минуту другой оператор спрашивает про срок возврата брака, и поиск приносит две версии регламента: старую с 14 днями и действующую с 30. Обе проблемы решаются в одном месте: до поиска, а не после ответа.
:::

## Фильтр по правам до поиска

Права проверяются на уровне документа, а применяются к фрагментам: каждый фрагмент наследует поле `access` своего документа. Правильное место для проверки находится перед поиском. Поиск вообще не видит фрагментов, которые пользователю нельзя читать.

```ts
export function allowedChunks(e: Engine, cfg: Config): Set<string> {
  let docs = e.docs;
  if (cfg.acl === 'before') docs = docs.filter((d) => canRead(cfg.role, d));
  if (cfg.freshness) docs = currentDocs(docs, cfg.asOf);
  // ...
}
```

Для роли оператора из {{acl.chunksSenior}} доступных старшему смены фрагментов остаётся {{acl.chunksAll}}: {{acl.hidden}} фрагмента двух закрытых регламентов исчезают из поиска целиком.

Посмотрим, что происходит с вопросом про компенсацию в трёх вариантах.

**Фильтр до поиска.** Закрытых фрагментов в выдаче нет. Помощник нашёл открытый регламент эскалации и ответил: «Обращение передают старшему смены, если покупатель требует компенсацию». Это полезный и допустимый ответ.

**Без фильтра.** Помощник ответил: «Старший смены может начислить покупателю компенсацию до 500 бонусов…». Это утечка: оператор узнал сумму, которую ему знать не положено, и, вероятно, перескажет её покупателю.

**Фильтр после поиска.** Поиск взял {{acl.postTop}} лучших фрагмента без учёта прав, а затем закрытые выбросили. Осталось {{acl.postKept}}. Утечки нет, но контекст опустел: закрытые фрагменты заняли места, которые могли достаться открытым. На вопросах, близких к закрытой теме, такой фильтр систематически оставляет модель почти без контекста. Если фильтровать после поиска, приходится запрашивать с запасом, и запас никогда не гарантирован.

Худший вариант, который встречается на практике, называется «фильтр после генерации»: модель отвечает по всем документам, а потом код пытается вычистить из ответа закрытое. Модель уже перемешала сведения, и отделить их по тексту ответа нельзя.

::: {.warn data-title="Типичная ошибка"}
Написать в системном промпте «не раскрывай сведения из документов для старших смен» и положить эти документы в контекст. Модель не система контроля доступа: инструкцию можно обойти, задав вопрос иначе, а иногда она нарушается сама. Права проверяет код до того, как текст попал в запрос. Модель не должна видеть того, что не должен видеть пользователь.
:::

Есть и тонкость. Лаборатория держит один индекс на всех и считает IDF по всем фрагментам, включая закрытые. По весам слов теоретически можно догадаться о существовании закрытых документов. Для поддержки магазина этим можно пренебречь; для документов, само существование которых секретно, строят отдельные индексы на каждую группу доступа. Тот же принцип касается кеша ответов: ключ кеша обязан включать роль, иначе ответ старшему смены достанется оператору, и дату актуальности, иначе кеш выдаст правило другого дня (глава 12).

## Версии и дата актуальности

У {{corpus.versioned}} правил «Полки» есть по две версии. Каждая версия хранит дату вступления в силу `validFrom`, временные правила ещё и дату окончания `validUntil`. Функция `currentDocs` выбирает из каждой группы последнюю версию, которая уже вступила в силу на заданную дату.

```ts
export function currentDocs(docs: Doc[], date: string): Doc[] {
  const best = new Map<string, Doc>();
  for (const d of docs) {
    if (!validOn(d, date)) continue;
    const cur = best.get(d.group);
    if (!cur || d.version > cur.version) best.set(d.group, d);
  }
  return docs.filter((d) => best.get(d.group) === d);
}
```

Документов в корпусе {{fresh.total}}, на 10 ноября 2026 года из них действуют {{fresh.current}}, а отсеяны {{fresh.hidden}}: две заменённые версии, регламент, который вступит в силу 1 декабря, и закончившаяся акция «Чёрная пятница 2024».

Без фильтра версий вопрос про брак показывает, зачем всё это. Старая версия регламента оказалась на месте {{fresh.v1Rank}}, действующая на месте {{fresh.v2Rank}}: тексты об одном и том же и теми же словами (хотя общих шинглов мало, глава 2), и поиску нечем их различить. Ответ помощника: «Покупатель может вернуть товар ненадлежащего качества в течение 14 дней с момента получения `[1]`». Ответ опирается на источник, ссылка верна, проверка опоры его пропускает. И он неверен.

Ещё два случая из того же опыта:

| Вопрос | Без фильтра версий | С фильтром на 10.11.2026 |
|---------------------------------------------|---------------------------------------------|---------------------------------------------|
| сколько дней на возврат товара надлежащего качества во время акции | первой в контексте стоит акция: «…увеличен до 30 дней» | акции нет, первым стоит регламент: «…14 дней…» |
| сколько дней заказ хранится в пункте выдачи | в выдаче обе версии, 5 и 7 дней | «…5 дней» сегодня, «…7 дней» при дате 15.12.2026 |

Последняя строка показывает, что дата актуальности нужна и в запросе, а не только в индексе. Оператор, который 28 ноября отвечает покупателю, забирающему заказ 3 декабря, может захотеть узнать правило на дату получения. На всём тестовом наборе фильтр версий поднял число верных ответов с {{fresh.correctOff}} до {{fresh.correctOn}} из {{aq.total}}.

## Удаление и переиндексация

Регламент отменили. Его надо убрать из индекса так, чтобы он перестал находиться немедленно, а не после ночной пересборки. Хорошая практика складывается из трёх шагов: документ сначала помечается неактивным (поиск его фильтрует), затем его фрагменты удаляются из индекса, затем проверяется, что поиск по его характерной фразе ничего не находит. Последний шаг стоит автоматизировать: удаление в векторных базах часто асинхронное, и «удалённый» фрагмент может какое-то время ещё попадаться в выдаче.

Переиндексация после правки документа устроена так же: новая версия попадает в индекс, старая помечается заменённой. Как пересчитывать только изменившееся, описано в главе 12.

## Практика

1. Храните у документа `access`, `validFrom`, `validUntil`, `version` и `group`. Без них документ не индексируется.
2. Фильтруйте по правам и дате до поиска, на уровне запроса к индексу.
3. Не доверяйте модели скрытие закрытых сведений.
4. Включайте роль и дату актуальности в ключ кеша.
5. После удаления документа проверяйте автоматически, что он больше не попадается в выдаче.
